# 提案 14 任務：ci-ai-review

規格見同目錄 `規格.md`。一條任務做完並打勾就 commit 一次。

## 任務

- [ ] 1. 使用者申請 Gemini API key，存進 repo Secrets 的 `GEMINI_API_KEY`。
      （使用者自己操作；Claude 只提供步驟。）
      驗收：Secrets 頁面看得到 `GEMINI_API_KEY`。

- [x] 2. 建立 `.github/workflows/ai-review.yml` 骨架：PR 開啟／推 commit 時觸發，
      設好最小權限，只印出 PR 編號與 diff 行數。
      驗收：開一個測試 PR，Actions 頁面看到 workflow 跑成功。

- [ ] 3. 取得 PR diff 並呼叫 Gemini（一次呼叫），先把回覆印在 workflow log。
      含 diff 過大截斷、fork PR 跳過、429 時略過並不讓 workflow 失敗。
      先放一版極簡 prompt 讓流程跑通。
      驗收：測試 PR 的 log 裡看到 Gemini 的 review 內容。

- [ ] 4. 把回覆貼成 PR 留言，結尾藏標記記錄被審的 HEAD。審查起點改讀 PR 上最近一則
      帶標記的留言（取代骨架裡用事件的 `before`），找不到標記或 commit 已不存在時
      退回審整個 PR，起點等於目前 HEAD 就跳過。
      驗收：同一個 PR 推第二個 commit，新留言只評論第二個 commit 的內容；
      不改檔案直接重跑 workflow，不產生新留言；
      force-push 後會退回審整個 PR；
      自己手動貼一則帶假標記的留言，下次審查仍照舊審，不被誘導跳過。

- [ ] 5. 寫 `.github/ai-review-prompt.md`：依規格「審查角色」寫入前端、後端、資安、
      架構四個視角，資安為條件式規則，並含輸出要求（三級嚴重度、定位到行、繁體中文）。
      驗收：用一個刻意含 `v-html` 的測試 diff，資安視角會指出 XSS 風險；
      一般 diff 不會出現與內容無關的資安意見。

## 完成條件

五條全打勾，用一個真實 PR 完整跑過「開 PR → 收到留言 → 推 commit → 收到只評論新改動的留言」。
