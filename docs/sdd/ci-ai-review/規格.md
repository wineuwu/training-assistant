# 提案 14：ci-ai-review

開 PR 時，GitHub Actions 自動把 diff 送給 Gemini 做 code review，結果貼回 PR 留言。

## 目標

跑通「PR 事件 → workflow → 取得 diff → 呼叫外部 AI API → 留言回 PR」這條流程，
學會 workflow 的觸發條件、權限、Secrets 三件事。

## 不做

常駐 bot、自架 server、Docker、逐行 inline 留言、自動修改程式碼、
擋 merge（review 只是建議，不設為必過檢查）。bot 化見提案 15。

## 行為

- 觸發：PR 開啟（`opened`）與後續推 commit（`synchronize`）時，目標分支為 `master`。
- 來自 fork 的 PR 拿不到 Secrets，此情況直接跳過，不報錯。
- 送給 Gemini 的內容只有「這次新增的 diff」，不重審已審過的部分。
  「上次審到哪個 commit」記在 bot 自己的留言裡：每則留言結尾藏一個
  HTML 註解標記（例如 `<!-- ai-review:sha=<被審的 HEAD> -->`），畫面上看不到。
- 審查起點的決定（PR 開啟與推 commit 共用同一套）：
  - 讀這個 PR 上 bot 最近一則帶標記的留言，取出標記裡的 commit 當起點，
    diff 範圍是「起點 → 目前 HEAD」。只採信作者為 `github-actions[bot]` 的留言，
    其他人貼的標記一律忽略，避免被假標記誘導而跳過審查。
  - 找不到標記（第一次審）或標記的 commit 已不存在（force-push、rebase），
    起點改為 `master`，審整個 PR。
  - 起點等於目前 HEAD（例如只是重跑 workflow），跳過，不呼叫 Gemini。
- 不依賴事件給的「推之前的 HEAD」：若某次推送的審查失敗了，下一次仍會從
  「最後一次成功審查的 commit」開始，中間的改動不會被漏掉。
- diff 過大時截斷到上限，並在留言註明「已截斷」。
- 輸出：每次審查貼一則新留言，標題註明審查的 commit 範圍，結尾帶標記。
  舊留言保留不覆蓋，每則只講新改動。
- 每次審查只呼叫 Gemini 一次，prompt 內同時要求四個角色的視角（見「審查角色」）。
- Gemini 回 429（額度用完）時：不重試、不降級，workflow 視為成功，
  並在 PR 留一則說明「額度用完，這次略過」（不帶審查標記，下次仍會從上次成功的起點審）。
- 其他失敗（網路錯誤、回應格式異常）：workflow 顯示失敗，但不影響 PR 其他檢查。

## 審查角色

四個視角寫在同一份 prompt 內，各自有專屬的知識背景與觸發條件：

| 角色 | 重點 |
|---|---|
| 前端 | 元件邊界與拆分、狀態放哪一層、目錄組織、何時抽共用、`<script setup>` 寫法一致 |
| 後端 | FastAPI、Pydantic、REST 慣例、SQL 與 SQLAlchemy |
| 資安 | 見下 |
| 架構 | API / service / repository 分層、耦合、破壞性變更 |

資安角色採條件式：diff 碰到特定內容才啟動對應檢查，避免現階段產生雜訊。

- 動到 Dockerfile、workflow、`.env`、CORS、相依套件 → 上線部署資安（secrets 外洩、容器權限、CI 權限）。
- 出現 `v-html`、`innerHTML`，或把使用者輸入渲染到畫面 → XSS。
- 出現 agent 讀取使用者輸入（如課表）或呼叫 tool → prompt injection 與 tool 權限範圍。

輸出要求：只留可行動的問題並定位到檔案與行；分 critical / warning / suggestion 三級；
不挑格式與個人偏好；使用繁體中文。

## 需要的東西

| 項目 | 說明 |
|---|---|
| Gemini API key | 在 Google AI Studio 申請的免費 key，由使用者自己申請 |
| `GEMINI_API_KEY` | 存在 repo 的 GitHub Secrets，不寫進任何檔案 |
| workflow 權限 | `pull-requests: write`（留言用）、`contents: read` |
| 設定檔 | `.github/workflows/ai-review.yml` |
| review 指示 | 一份 prompt 檔，告訴 Gemini 這個專案要看什麼 |

## 取捨

- 資料去向：diff 會送到 Google，且免費方案的資料可能被用於改進產品。
  這是個人練習專案，可接受；不要在 diff 裡放 key 或個資。
- 免費額度有上限，PR 頻繁時可能失敗，屬預期，不做重試機制。
- 純 Actions 不需要 server，代價是每次都是全新環境，沒有跨 PR 的記憶。
