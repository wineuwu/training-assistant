# 03 工具鏈

虛擬環境、套件管理、格式化、測試。跟語言無關，但不會用就寸步難行。

## 虛擬環境

**Python 的套件預設裝在系統裡，全域共用。** 不隔離的話，
A 專案要 fastapi 0.100、B 專案要 0.140，就只能二選一。

虛擬環境 = 一個專案專屬的資料夾，裡面有自己的 Python 和套件。
對應 JS 的 `node_modules`，差別在 JS 是自動隔離的，Python 要手動建。

```
backend/
├── .venv/              ← 虛擬環境，不進版控
├── pyproject.toml      ← 宣告需要什麼套件（對應 package.json）
└── uv.lock             ← 鎖定實際版本（對應 package-lock.json）
```

`.venv/` 一定要寫進 `.gitignore`。

## uv

套件管理工具，對應 JS 的 pnpm。取代舊的 `pip` + `venv` + `pip-tools` 組合。

```bash
uv add fastapi              # 安裝並寫進 pyproject.toml
uv add --dev pytest         # 只在開發時需要
uv remove fastapi           # 移除
uv sync                     # 照 lock 檔還原環境（clone 下來第一件事）
uv run python main.py       # 在虛擬環境裡執行
uv run pytest               # 同上
```

**`uv run` 的意義：** 自動用專案的虛擬環境跑，不用先 activate。
沒有它就要 `source .venv/bin/activate`，忘了 activate 是很常見的錯誤來源。

### --dev 是什麼意思

分成兩組相依：

| | 進 Docker image | 例子 |
|---|---|---|
| 一般 | 會 | fastapi、pydantic |
| `--dev` | 不會 | pytest、ruff |

正式環境不需要測試框架和格式化工具。分開宣告能讓 image 小一點、
攻擊面少一點。對應 JS 的 `dependencies` vs `devDependencies`。

### pyproject.toml

現在 Python 的設定集中在這一份，不像以前每個工具一個 dotfile：

```toml
[project]
dependencies = ["fastapi>=0.141.0"]

[dependency-groups]
dev = ["pytest>=9.1.0", "ruff>=0.16.0"]

[tool.pytest.ini_options]           # pytest 的設定也放這
...
```

## Ruff

formatter + linter，一個工具抵 Prettier + ESLint + isort。Rust 寫的，很快。

**Prettier 不支援 Python**，它是 JS 生態的工具，沒有 Python parser。

```bash
uv run ruff format .            # 排版
uv run ruff check .             # 找問題
uv run ruff check --fix .       # 找問題並自動修
```

### format 和 check 是兩件事

| | 管什麼 | JS 對應 |
|---|---|---|
| `format` | 空白、換行、縮排 | Prettier |
| `check` | 程式碼問題、import 排序 | ESLint + isort |

import 排序歸在 check 而不是 format，因為調換 import 順序理論上
可能改變執行結果（有 side effect 的 module），屬於「改語意」。

### 規則代號看得出出身

| 前綴 | 來源 | 性質 |
|---|---|---|
| `F` | Pyflakes | 確定會出錯（用了沒定義的名字） |
| `E` / `W` | pycodestyle | 風格 |
| `I` | isort | import 排序 |

輸出裡的 `[*]` 代表這條可以自動修。

### 編輯器整合

裝 VS Code 的 Ruff extension，加上專案設定就能存檔自動格式化：

```json
{
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",
    "editor.formatOnSave": true,
    "editor.codeActionsOnSave": {
      "source.organizeImports.ruff": "explicit"
    }
  }
}
```

**這對 Python 特別重要**，因為縮排就是語法——排版錯誤等於程式錯誤，
不該靠眼睛盯。

`.vscode/settings.json` 建議進版控（格式化規則是專案共識，
不是個人偏好）。`.gitignore` 要注意：父層目錄被忽略時子檔案的 `!` 無效，
得寫 `.vscode/*` 而不是 `.vscode/`：

```
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
```

## pytest

```bash
uv run pytest               # 跑全部
uv run pytest -v            # 顯示每條測試
uv run pytest test_x.py     # 只跑一個檔
uv run pytest -k "menu"     # 只跑名字含 menu 的
```

### 自動探索規則

pytest 靠命名找測試，不用註冊：

- 檔名 `test_*.py` 或 `*_test.py`
- 函式名 `test_*`
- class 名 `Test*`

名字不符就**完全不會被執行**，而且不會警告——測試「都過了」有時是
根本沒跑到。數量對不對要看輸出的 `collected N items`。

### assert 就夠了

```python
def test_health():
    response = client.get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

沒有 `expect().toBe()` 這類 API，就用 Python 的 `assert` 關鍵字。
pytest 會改寫 assert，失敗時自動印出兩邊的實際值，不用自己 print。

**dict 和 list 可以直接 `==` 比內容**（見 `01-語言核心.md`），
所以比對 JSON 回應很方便。

### 測「應該失敗」的情況

```python
import pytest

def test_invalid_input():
    with pytest.raises(ValidationError):
        Training(date="2026-03-10", type="hiit")
```

意思是「我預期裡面會丟這個例外」。**沒丟也算失敗**，會顯示 `DID NOT RAISE`。

這比手寫 try/except 好：

```python
try:
    ...
except:
    pass        # 程式沒報錯時測試也會過 → 假綠燈
```

### 測什麼、不測什麼

**判準：這條測試如果掛了，我學到什麼新資訊？** 沒有新資訊就別寫。

| 層次 | 測什麼 | 抓得到 |
|---|---|---|
| 單元（直接呼叫函式／建 model） | 邏輯**寫對**了嗎 | 規則本身的錯 |
| 整合（打 API） | 邏輯**接上**了嗎 | 路由沒接、錯誤被吞、狀態碼錯 |

單元測試全綠不代表 API 真的有擋——這是常見的假安全感。

**一般分工：** 規則的各種分支放單元測試（便宜、快、定位精準），
每支 API 挑一兩條代表案例（一成功一失敗）。
不是把所有分支在 API 層再跑一遍，那是重複：改一條規則要改兩處測試，
抓到的 bug 卻沒變多。

### 會失敗過的測試才可信

新寫的測試如果一次就綠，有可能是它根本沒在驗東西。
**故意改壞 code 看它掛掉**，是確認測試有效的標準手法。

## FastAPI 的 TestClient

```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)

def test_health():
    response = client.get("/health")
```

**不會真的起 server、不佔 port。** 它把 request 物件直接餵給 app，
所以很快，也不用處理「等 server 起來」的問題。

用法跟 `fetch` 很像：`client.get(...)`、`client.post(url, json={...})`，
回傳物件有 `.status_code`、`.json()`、`.text`。
